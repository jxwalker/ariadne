# Durable private activity ingestion

Python 3.11+ standard library, SQLite WAL with `synchronous=FULL`. No pip packages or container images are required by this service. Existing Node console generation and read-only collectors remain separate. `ariadne` remains the canonical TypeScript runner.

## Contract and authentication

[Producer schema](../../schemas/activity-event-v1.json) and [controlled cloud example](../../examples/activity/task-start.json). Server receipt timestamp is assigned on acceptance and returned as `receivedAt`; never accept producer-selected receipt times. Raw validated bytes and canonical envelope remain in private SQLite, never full transcripts. Extra fields, sender-selected commands/paths, non-HTTPS evidence links, credential-bearing URLs, malformed timestamps, oversized labels and payloads are rejected. Changed filenames in legacy console are observations, not authorship.

POST `/ingest/v1/events`, JSON, maximum 64 KiB, headers `X-Ariadne-Source`, `X-Ariadne-Timestamp` (Unix seconds), `X-Ariadne-Nonce`, `X-Ariadne-Signature` (hex HMAC-SHA256). Sign exact bytes of `timestamp + "\n" + nonce + "\n" + body`. HTTPS certificate verification is mandatory. Request timestamp tolerance is 300 s. Durable nonce digest bindings expire after 600 s; identical retransmission is idempotent. Event IDs never expire automatically and must not be reused; different content is rejected. Source/project/repository scopes come from protected credential config, independently of supplied agent identity. An agent identity is a source assertion, not independently authenticated authorship. Limit 120 requests/minute/source, persisted across service restart. Credentials reload per request: revoke with `revoked: true`, rotate a secret atomically in the mode-0600 file, then update the sender. Never put credentials in Git, vault, browser code or screenshots.

SQLite commit precedes 202; duplicate identical event returns 200 and original receipt. Projection worker runs every 0.5 s, batches at most 200 events. Restart replays unprocessed queue. Sequence order governs projection; occurrence clocks are evidence only. Gaps are shown, late lower sequences retained without changing current state. Run source/project/repo/task/parent/agent identity cannot change. Terminal completion/failure cannot be revived by higher sequences; a new run is required. `session.end`, `subagent.end`, and stopped responses mean unknown, not completed. Child lifecycle never changes parent state. Heartbeats preserve blocked/interrupted state. Working runs with no accepted event for 90 s become stale/unknown. Source connectivity and agent task state are separate. Completion grants no merge, review, or mutation authority.

## Native adapters and capability boundaries

References checked 12 Oct 2026: [Claude hooks](https://code.claude.com/docs/en/hooks), [Codex hooks](https://learn.chatgpt.com/docs/hooks), [Grok plugins](https://docs.x.ai/build/features/skills-plugins-marketplaces). Historical JW-MBP versions: Claude 2.1.50, Codex CLI 0.31.0. On codex-dev, Claude Code 2.1.296 and Codex 0.162.1 have been capability-checked locally. Real repository reviews use the generic wrapper with existing permission controls; no global hook settings are replaced. Current official Codex documentation describes `hooks.json` and lifecycle hooks, but native hooks are not installed by this verification. Current documentation does not prove old Codex supports hooks: leave its native adapter pending until capability-checked upgrade approval; existing read-only session collector is supported. Grok hosted operators must establish whether their cloud runner supports custom HTTPS clients; CLI skills do not establish that capability.

`activity_sender.py --config <0600 file> hook` reads bounded stdin and queues only lifecycle name, session/child ID and operator-selected metadata after exact workspace scope check. It never reads transcript paths, prompts, tool arguments, output or files; returns without network delivery. Add opt-in project-local hook config only after reviewing existing settings. No automatic settings replacement or permission change. Supported mappings: SessionStart/start session; UserPromptSubmit/start task; PreToolUse/PostToolUse/progress; PostToolUseFailure/progress with tool error; Stop/progress with unknown completion; SessionEnd/end session; Interrupt/interrupted where documented; SubagentStart/Stop/child lifecycle. Unsupported events are omitted. Hooks alone do not maintain long-tool heartbeat: run through the generic wrapper or run a separately supervised heartbeat integration. Spool maximum 1000 events, worker every 2 s, capped retry backoff 300 s; delivery never triggers model/tool execution. Pending authorization is needed to install hooks on existing Macs.

Generic sender modes: `event`, `flush`, `worker`, `run -- <operator-selected command>`. Wrapper queues a start and 15 s heartbeats for long tools; exit zero is progress, never automatic completion. `event --kind task.completed` explicitly reports completion. Sender config supplies source, secret, endpoint, spool, agent, project, repo, label and optional branch; protected outside repo. Server never executes sender commands. Lost offline events can be retried with new request signatures and original event IDs.

The new surface suppresses legacy prompt-derived task labels; imported snapshot labels are metadata-only agent/repository labels. Dashboard/API task text is always metadata-only (agent product and repository); it does not return supplied labels or summaries. Optional operator `snapshotRunRefs` bind exact registered host/session run hashes to independently checked branch/SHA/PR metadata; they never establish authorship. Existing port18092 output is preserved and not exposed publicly. Operator-selected native task labels remain in private stored evidence, but are omitted from dashboard JSON. The optional snapshot importer uses exact operator-mapped host/session IDs, preserves source provenance as `read-only collector`, and never labels those observations native hooks. Legacy snapshot section and durable section are different evidence views of the same session, not counts to sum. Hook correlation requires an operator-approved `correlationHost` on each source registration plus exact repository, agent product and session ID. Known CLI display aliases (`Claude Code`/`Claude`, `Codex CLI`/`Codex`) normalize only for correlation; raw envelopes retain the original name. A wrapper run can be bound to its real session ID after inspecting the CLI result/session-start record; never infer a session from branch, author or timing. The durable view combines matching timelines and prefers native reports over polled observations; cloud sources without a registered host mapping remain separate. The legacy snapshot view stays available as the collector evidence view.

## GitHub evidence

Webhook `/ingest/v1/github` validates `X-Hub-Signature-256` with constant-time comparison over exact raw bytes, dedupes `X-GitHub-Delivery`, commits before acknowledgement, and processes outside requests. Supported push, pull_request, pull_request_review, workflow_run, check_run/check_suite, issues/issue_comment and ping. Repo allowlist applies. GitHub timestamp signing differs from agent contract: GitHub has no producer timestamp signature; preserve delivery IDs and use GitHub redelivery. [Official validation contract](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries).

`activity_reconcile.py` uses existing host `gh` credential, paginates every PR and associated task review/check pages, stores private API observations and per-repo health; no 40-PR truncation. Install a scoped GitHub App when available; existing auth is never copied. Branch/SHA/PR matching is association only, not attribution. Webhook installation and public route require separate operator/provider configuration. Explicit `Ariadne-Task: <id>` or `Ariadne-Run: <id>` lines in PR/issue/comment text associate evidence with that task/run; they do not grant authorship. Workflow-only reconciliation remains pending.

## Wrapper heartbeats and freshness

The wrapper queues task start, then heartbeats while the subprocess runs, waiting 15 seconds between delivery attempts. Delivery delays can extend this interval. Accepted higher-sequence heartbeats refresh visibility without changing blocked, interrupted or terminal states. Working runs display stale/unknown after 90 seconds without a projection-refreshing event; missing freshness is not completion. Blocked and interrupted runs retain their task state even when their source becomes stale. A later accepted heartbeat can restore freshness after staleness. Process exit zero reports progress, not completion; completion requires an explicit report and delivery still requires independent evidence.

## Lifecycle signals do not verify delivery

Process exit, a stopped response and session end are lifecycle observations. The wrapper reports exit zero as progress; a nonzero exit reports terminal agent failure. Only an explicit `task.completed` reports completion, and it remains an agent assertion. Heartbeats preserve blocked and interrupted states; later progress returns nonterminal runs to working, while session end sets them to unknown. Working runs without a fresh accepted projection event for 90 seconds become stale/unknown. Verify delivery separately through PR, CI and review evidence. No lifecycle signal grants merge, review or mutation approval.

## Insights dashboard and private read APIs

The insights-first view is injected ahead of the static console. Live now groups fresh working/blocked reports by agent product and machine; source chips combine friendly display names and retain counts for distinct registrations. Configure optional `displayName` per registration (or use its approved `correlationHost`). Collector session cards remain above repository activity, collapsed as historical evidence. The console embeds the existing SVG mark and suppresses prompt-derived task/update text in both rendered cards and embedded JSON. The server also sanitizes older console HTML. PR check lists expand on demand. No CDN assets or public read endpoints are used.

GET `/api/insights?range=24h|7d|30d` returns metrics, UTC charts, breakdowns, factual callouts, filter choices and live reports. GET `/api/runs` accepts the same range plus `page`, `pageSize`, `repo`, `agent`, `machine`, `source`, `state`, metadata `text`, `group=machine|repo`, `snapshots=show`, and `stale=show`. Snapshots and stale runs are hidden by default; page size is 20 (maximum 100). GET `/api/sources` returns safe source status, never credentials. The legacy `/api/activity` uses the sanitized insights contract. There are no POST actions on these APIs. The external JavaScript asset is served by the private server with `script-src 'self'`; polling preserves filters, pagination, scroll and open evidence drawers and pauses via the Page Visibility API.

Ranges use **server receipt/observation time**, not producer clocks. Native run totals include runs whose latest receipt falls in range; exact approved host/repository/product/session matches prefer native metadata and retain both timelines. Snapshot-only runs have their own count and are excluded from native KPIs. Active hours sum each native run's observed first-receipt-to-terminal/latest-receipt span clipped to the range; concurrent spans overlap and are not CPU or billed hours. Median/p90 (linear interpolation) and the histogram use completed/failed receipt spans ending at the first accepted terminal report. Success/failure/unknown-interrupted rates use all native runs as the denominator; ongoing runs are counted separately in outcomes. Unknown includes stale and ended-without-completion runs, not a proven process abort. Events/hour includes every accepted event in range, including snapshots and correlated producers. Daily/weekday charts assign carry-in runs to the range boundary and use UTC. No missing dates or absent observations are invented as evidence.

GitHub counts deduplicate commit IDs from stored push payloads, PR numbers from stored PR observations and terminal CI IDs per check/workflow/suite kind. Repeated reconciliation polls do not create new PR/CI counts. These are *observed PRs*, not newly opened PRs; reconciliation does not yet collect commit histories or workflow-only data. CI pass rate divides successful terminal results by all observed terminal results (including neutral/skipped/cancelled). Failure streak callouts use collection order and stop at timestamp ties containing a non-failure; they are not inferred chronological workflow execution histories. Run drawers show at most 30 lifecycle events and 10 exact repository + PR/branch/commit associations in range, with safe links, never GitHub bodies, titles or prompt text. Lifecycle completion remains an agent assertion and grants no mutation authority.

Callouts cite their counts: busiest native agent/machine/repo, unfinished runs quiet for over 30 minutes, non-revoked sources quiet for over 2 hours, never-connected registrations, recorded sequence gaps, and consecutive observed CI failures. Empty states mean evidence is absent, not zero verified activity. Query strings are capped at 2 KiB / 20 fields, page number at 10,000, projections at 10,000 runs / 50,000 lifecycle events / 50,000 observations; `truncated` and a visible warning identify partial aggregates. Source status is current regardless of selected range.

**Public boundary stays unchanged.** `deployment/activity/public-ingestion.nginx.example` proxies only the anchored `/ingest/v1/(events|github)` route with `limit_except POST { deny all; }`, to the separate `ingestOnly=true` listener. All other locations return 404. `test_public_nginx_allowlist_excludes_insights` asserts the exact regex, POST restriction, fallback denial, and rejection of all read APIs/assets. HTTP tests also prove that `ingestOnly` rejects these GET routes and the JavaScript asset. Do not add a GET exception or proxy the private 18095 listener publicly; use the existing private Tailscale Serve route.

Install `activity_server.py`, `activity_insights.py`, `activity_dashboard.html`, and `activity_dashboard.js` together in the same release directory; regenerate configured `consoleHtml` with the updated `src/consoleHtml.ts`. No configuration migration, schema migration or proxy change is needed. Deployment remains an operator action through the approved mutation gate. `scripts/check_activity_dashboard.mjs http://127.0.0.1:18099` checks an isolated live-data copy at 1440/375px, including polling/pagination/filter/evidence continuity and simulated hidden-tab state; it writes local private evidence under `.insights-check/`.

## Orchestration control evidence

The primary **Orchestration evidence and controls** table shows current evidence independently of the activity time range. GET `/api/controls` is private and read-only, subject to the same ingest-only/public denial as the other GET APIs. The nginx allowlist stays unchanged. The static repository-only console links to this populated view rather than implying that its empty local control vault represents the whole system; its metric grid is collapsed under **Other vault metrics**. The activity log starts collapsed and opens for URL filters or an explicit user click. No control action, approval, command execution or external mutation is exposed by the dashboard.

Optional server config `controlEvidenceDirs` is an ordered list of absolute, read-only vault `control/` directories. Recommended **operator wiring only; not applied to production**:

```json
{
  "controlEvidenceDirs": [
    "/home/james/workspaces/ariadne-dev/vault/projects/ariadne/control",
    "/home/james/workspaces/ariadne/vault/projects/ariadne/control"
  ]
}
```

The server reads only approvals, mutation-readiness plans/audit, dry runs, executions, and live-adapter readiness/cutover JSON. It never copies or writes these records, and they must remain uncommitted. Same category/ID records across vaults use the latest explicit evidence timestamp; configured first directory wins ties. Singleton audits are identified by project. Dry-run/execution current status uses the latest attempt **per plan**, retaining previous attempt IDs/statuses/exit codes and the failed-then-passed history in drawers and record-cited Insights callouts. An execution reported passed still requires live exit zero and a passed post-verification result to grade pass. Pass describes evidence only and never overrides the full mutation gate. Requested/rejected approvals and blocked audits produce record-cited callouts; stale/missing controls cite their record or control identifier.

Freshness thresholds: approvals **30 days**; plans, mutation audits, dry runs, executions, adapter readiness/cutover and webhook deliveries **24 hours**; source accepted receipts, reconciliation and run receipts **2 hours**. Each row shows relative time, absolute UTC on hover, and its threshold. Missing timestamps remain missing; file modification times are not used to invent evidence times. A category aggregates latest record grades (fail, then missing, then stale, otherwise pass). Historical failed attempts remain visible even when a later result passes. These thresholds indicate review freshness, not approval expiry or permission revocation.

Records are projected through a nested field allowlist: identity/target/scope, approval references and decisions (who/when), statuses, exit codes, post-verification result, blockers, rollback and safe commands. All stdout/stderr bodies, environment, arbitrary extra fields and credential values are dropped. Any selected string with key/token/secret/auth material, recognized credential prefixes/JWTs, high-entropy token-like strings, shell environment assignments or known source credential values is replaced as a whole with `[redacted sensitive material]`. Commands are text only, never run or made actionable. Conservative redaction can also hide benign credential references and full hashes. Limits: eight configured directories, 1,000 files, 1 MiB per file, 200 control rows, latest 100 details per row, 50 array entries and bounded nesting/text. Symlinked folders/files are skipped; unreadable/missing directory and record warnings are surfaced without raw paths or bodies. Partial results are explicitly marked.

Database controls derive counts and timestamps from events/runs, webhook delivery metadata and per-repo reconciliation health, without reading raw webhook bodies. Source rows show registration, revocation, connection state and last accepted receipt; no protected credential values are returned. A scoped Grok source remains **provider-pending** until a stored cloud-located Grok event from that source exists with no controlled/test marker in source/run/task/label metadata; controlled test reports do not establish provider onboarding. Location/product remain source assertions, not independent proof of hosted execution. Revocation and provider-pending are separate states and may both appear.

Duplicate receipt counters are **unavailable**, not zero: the current schema deduplicates event/delivery IDs without persisting retry counts. Retained nonce and rate rows are shown as separate bounded-window evidence, never reinterpreted as duplicates. Reconciliation health stores the latest run per repo, not a complete run count/history. These coverage limits are explicit in the controls API and UI. Secret detection is conservative rather than a proof that arbitrary free text contains no secrets; keep credentials in protected storage and never embed them in records. Install `activity_controls.py` beside the existing server/insights module and dashboard assets during an approved operator deployment; no database migration, public route change or control-record commit is needed.
