# GitHub webhook proxy fix proposal

Assignment ARIADNE-MASTER-PILOT-20261014-P02. Plan only: do not deploy this template, reload nginx, restart services or alter tunnel/configuration. The proposed repository nginx example is not evidence of installed configuration.

The assignment reports ~91KB GitHub payload rejections. The repository template sets client_max_body_size 64k and proxies both routes with a five-second read timeout. Proposed exact location /ingest/v1/github alone gets 2m and proxy_read_timeout 35s; /ingest/v1/events retains 64k and 5s. GitHub's stated maximum is 25MB, but accepting every possible maximum payload is outside this bounded fix. 2MiB is about 23 times the observed 91KiB rejection, with room for larger pilot deliveries while preserving a modest unauthenticated request/memory limit. Capture actual delivery size distribution before changing this bound further; documented oversize deliveries require deliberate replay/reconciliation, never silently claimed coverage.

Crucial backend prerequisite: scripts/activity_server.py MAX_BODY is also 65536 and applies to BOTH routes. Proxy-only tuning still returns application 413. Before deployment, separately review/test the exact route-specific backend proposal: retain MAX_BODY=65536 for events and introduce GITHUB_MAX_BODY=2*1024*1024 selected only when self.path == '/ingest/v1/github'. Preserve raw bytes, X-Hub-Signature-256 HMAC verification, constant-time comparison, delivery ID/repository checks and duplicate-body conflict semantics unchanged. This PR prepares that change in the plan; it does not modify the deployed server or weaken signature checks. Pin both reviewed proxy and backend candidate hashes before approval.

The webhook path reads bounded bytes, parses JSON, verifies the raw-byte signature and repository, then Store.webhook durably inserts the raw delivery before 202 (200 for identical duplicate). A separate App.work worker invokes Store.process later. It already uses deferred processing: acknowledging before the durable insert would lose evidence on crash, so no memory-only fast acknowledgement is proposed. Store.connect waits up to 30 seconds for SQLite locks. Store.process holds BEGIN IMMEDIATE across batches of up to 200 events plus webhook processing; write contention is a plausible cause of exceeding the proxy's five seconds, not a proven diagnosis. Signature-file access, parsing, filesystem/durable commit latency and actual proxy/worker contention also need measurement. See webhook-proxy-evidence.json for bounded read-only journal excerpts and message hashes; absence of matching recent excerpts would not disprove the assignment's earlier observation.

Prefer 35-second GitHub-only proxy read timeout as an interim, bounded proposal matching the current 30-second DB wait plus handling margin. Do not change event/client/connect timeouts globally. Validate durable duplicate receipts under a synthetic write-lock delay, rejection/retry after exhausted lock wait, signature failure for changed raw bytes and process crash/restart recovery. Instrument request stages with duration/status/delivery hash only, no headers/body/secrets. Follow-up optimization should shorten worker write batches or persist into a durable intake queue with bounded processing transactions; it must retain raw evidence and not acknowledge uncommitted bytes. If measured load needs larger timeouts or queue changes, produce a new plan.
